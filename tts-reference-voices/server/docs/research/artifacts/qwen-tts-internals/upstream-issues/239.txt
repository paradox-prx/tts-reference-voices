--- comment by sherifhanna700 (NONE) 2026-08-28T18:40:58Z
We hit this while narrating long-form audiobooks with 1.7B-Base voice cloning and traced the mechanism through the code. Summary of what we found, measured (articulation = syllable nuclei per second of speech, first vs last third of each generation; seed pinned; identical text and sampling parameters across comparisons):

**Mechanism.** In simulated-streaming mode the target text is fed one token per codec frame (12.5 tok/s, `modeling_qwen3_tts.py`, trailing-text feed in `Qwen3TTSTalkerForConditionalGeneration.forward`), several times faster than speech consumes it (~4–5 tok/s). Early in generation the model can't speak ahead of the text it has received — an implicit pacing brake. The feed outruns consumption, the backlog grows, the brake vanishes, and the rate climbs toward the model's prior (~195 wpm in our runs, regardless of the reference's own pace across five references spanning 112–182 wpm).

**Long references remove the brake entirely.** `generate_icl_prompt` (streaming branch) feeds the concatenated ref+target text across the *reference's* codec frames — so a 12.9s reference (161 frames) delivers ~160 target-text tokens during the prefill, before the first generated frame. Rushing then starts at word one.

| configuration | drift within one ~25s generation |
|---|---|
| streaming, 12.9s ref | **+16.7%** |
| streaming, 4s slice of the same ref | **−2.3%** |
| non-streaming, same 12.9s ref | **0.0%** |

Additional structure we measured on raw output: the rate resets at sentence starts and climbs clause-by-clause within long sentences (+17% first-to-last clause across a 145-word sentence), with inter-clause pauses shrinking ~20% alongside — so listeners hear "starts composed, ends rushed" repeatedly.

**Inference-side repairs we tried and falsified** (all with the 12.9s reference, streaming):

1. Reference transcript only across the reference frames, pad after → instant EOS (~0.2s output). Pad-after-text at the generation boundary is the trained end-of-utterance signal.
2. Non-streaming-style block layout for the reference, then streaming the target text from generation start → instant EOS, same reason.
3. Reference transcript right-aligned against the reference audio's end (leading pad) → runaway generation: 655s of mostly silence for a 25s utterance.
4. Slowed feed (1 token per N frames, token injected once, pad frames between) → long silences and bursts; N=2 halves the rate but injecting on consecutive frames doubles words; fractional N destabilizes pacing (+124% drift).

Conclusion: the talker tolerates exactly one streaming prompt shape — contiguous text, left-aligned from frame 0 — so this doesn't appear fixable at inference time with current weights. A training-side change (randomized/pace-matched text-feed schedules, or reference-aligned ICL prompt layouts) seems required for rate-stable streaming.

**Practical workarounds** until then, in order of effectiveness:
- `non_streaming_mode=True` (flat pacing; this is already the default for CustomVoice/VoiceDesign) — PR #362 proposes making it the clone default too;
- if you need streaming, keep the reference under ~5 seconds;
- keep individual generation calls short (≤ ~30s of audio).
