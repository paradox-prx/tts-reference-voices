#89 [closed] Very slow inference on 5090
URL https://github.com/QwenLM/Qwen3-TTS/issues/89
created 2026-01-26T07:48:10Z by dur-randir

### Description

I have tried in the following environments: Windows 11, CUDA 13.1, python3.11+torch 2.9 and python 3.13+torch 2.10. In both cases, inference is 10 times slower than realtime. For the following text "Looks interesting but those Huggingface hub files are just annoying with all those extra json files." it takes over 50 seconds to generate audio with preloaded model, both from qwen-tts-demo and suggested python snippets from huggingface. I've checked that the model is loaded on cuda:0 device, but despite that GPU usage, observed through nvitop, remains ~4-5%.

- [x] The issue hasn't been already addressed in Documentation, Issues, and Discussions.

Hi! I will be releasing the full application, api client included soon, I'm giving the assistant tools and mcps at the moment, wiring it to frontend notifications.

I want to release it with once I have all this polished, but every day I find a new thing to implement 😃 

It has VAD, interrupts, wake word like "OK Google" and plenty of other features.

TTS is still the major bottleneck on my humble 16GB card.

How did I improved TTFB?

I tweaked the llm prompt to first answer the user with a short sentenced, then the rest.
I can gate that first sentence by punctuation,and send that first short sentence to the TTS to decode, then the rest, improving latency.

The TTS also is already receiving partial transcripts from the ASR instead of full transcriptions, so when the user starts to talk, I send few chunks of audio without the full context so ASR can start to work on transcription, and send that early too to the TTS.

When the user has finished talking the ASR has transcribed most of the text already and the TTS has also generated a lot since it started way earlier.

The 2 phase approach I implemented on my fork is the other main advantage, I've explained it [there](https://github.com/rekuenkdr/Qwen3-TTS-streaming). First phase emit frames are lower , and window decode too, that gives you faster TTFB with the caveat of also lower audio quality but most of the time it works perfect and you don't even notice.

That and CUDA graphs on almost everything(this was the hardest part, isolating without the whole thing exploding), PCM, prebuffering, websockets,warming up passes on runtime application for all 3 services (ASR,TTS and LLM).

The ASR is vllm backend on a sub-process (to isolate those CUDA graphs) and that is the only separated thing, everything is monolithic you could say, because I tried separating the ASR on an http server but even it was faster generating, only the communication added more latency. So nice and simple Unix sockets with Pickle (that support numpy arrays natively) is a win win on this situation and I dropped that separated approach (although I have a branch with that architecture too).

I hope this clarifies it, is not a simple fix, but tweaking many, including the qwen library, because I'm GPU poor you could say, so where there is necessity, creativity appears. 😃 

I'll be open sourcing the whole thing soon, I'll be in touch.
